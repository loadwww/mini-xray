# M2 · HTTP 实战

### 1. TCP 是字节流，不是消息流——这意味着什么？

- `recv` 一次返回多少字节，**只取决于内核缓冲区当时有多少**，与"一条 HTTP 请求"没有任何对应关系
- 三种必然出现的情况：正好一个请求、**半个**请求（半包）、**一个半**请求（粘包）
- 所以"一次 recv 对应一条消息"的假设是错的，任何基于它的代码都会在慢网络 / 大 body / 代理链路上崩
- 推论：**报文边界必须自己在字节里找**——这是所有应用层协议的共同工作

### 2. `recv` 的返回值为什么必须保留三值？

- `> 0` 读到这么多字节（可能只是一部分）；`0` 对端**正常关闭**（FIN）；`SOCKET_ERROR` 出错（查 `WSAGetLastError()`）
- 压成 `bool`：`0`（读完了）和 `-1`（真错误）合并成 `false`，两种完全不同的走向分不开
- 压成 `string`：丢掉"这次只读到一部分"这个事实，调用方以为拿到了完整响应
- 不在 `recv` 内部循环到读满：**只有调用方知道什么算读完**（HTTP 靠 `\r\n\r\n` + Content-Length，SSE 永远不该等读满）。边界判断属于解析层，不属于传输层

### 3. HTTP 报文边界怎么判？

- 头结束标志是 `\r\n\r\n`（空行）；`pos + 4` 之后是 body 的起点
- body 长度：有 `Content-Length` 就按它凑；用 `Transfer-Encoding: chunked` 则是一段段"十六进制长度\r\n数据\r\n"，以 `0\r\n\r\n` 结束（**SSE / 流式响应基本都是 chunked**）
- header 名**大小写不敏感**（`Content-Length` / `content-length` 等价），用 map 存时要么统一大小写，要么用不敏感比较
- 值的前导空格属于分隔符不属于值；行尾 `\r` 属于行终止符不属于内容

### 4. 为什么"从上次位置往前退 3 字节"重找不会漏？

- 逐块 `find("\r\n\r\n")` 时，分隔符可能被切成 `…\r\n\r` | `\n…` 两半
- 若从"上次扫到的长度"原位置继续找，`\r\n\r\n` 的起点就在这个位置**之前 3 个字节**，永远找不到 → 死等
- 分隔符长 4，最坏情况前 3 个字节落在上一块，所以退 3 能覆盖所有切法；退 4 也行（多扫 1 字节），退 2 会漏
- 代价是最坏 O(n²) 重扫；生产级解析器换成**增量状态机**（每个字节只看一次）

### 5. 服务端连接和客户端连接为什么能共用一个 `Socket` 类？

- 两者的差别只在"句柄从哪来"：客户端 `socket() → connect()`；服务端 `accept()` 返回**已经连上**的句柄，绝不能再次 `connect`（`WSAEISCONN`）
- 做法：私有 tag 构造函数 + `static Socket adopt(SOCKET)`，把"接管现成句柄"变成一个显式、唯一的入口
- 反面做法：公开 `setHandle()`——句柄来源变成随时可改的状态，析构重复关闭就出现了
- 移动之后源句柄置 `INVALID_SOCKET`、析构"有效才关"，是 double-close 的唯一防线

### 6. HTTP 库替你做了什么？

1. **keep-alive 连接复用**：一条 TCP 连接上循环"解析请求 → 处理 → 写响应"，直到超时或对端关闭。省掉反复握手与慢启动；前提是每次响应必须**精确写完**，多写/少写一个字节下一条请求就错位
2. **线程池**：accept 后把连接丢给空闲工作线程，主线程继续 accept。手写串行版一个慢请求挡住所有后续连接；线程池还有上限语义，避免连接暴涨时线程数失控
3. **完整报文解析**：chunked 编码、header 折行、`Expect: 100-continue`、body 的多种结束方式
4. **URL 解码与查询参数**：`/a%20b` → `/a b`，`?a=1&b=2` 解析成键值
5. **header 大小写归一 + 重复 header 处理**（如多个 `Set-Cookie`）
6. **超时与错误恢复**：读写超时、空闲连接清理、对端 RST
7. **响应构建细节**：自动 `Content-Length`、状态原因短语、`Date` 等

### 7. 为什么生产代码不自己写 HTTP 解析器？

- 不是"会写错"——覆盖正常请求的解析器确实能写对；问题是**边缘情况与攻击面的数量级**
- 恶意输入：超大 header（内存耗尽）、**慢速攻击**（几秒发一个字节，占住你的线程）、`Content-Length` 与 `Transfer-Encoding` 同时出现且互相矛盾（**请求走私**的根源）
- 代理特有的坑：hop-by-hop header（`Connection`、`Transfer-Encoding` 等）必须剥掉不能透传；"解析后再序列化"若与对端理解不一致，就制造走私
- 经济性：解析器是"写完基本不改"的基础设施，但 RFC 更新与安全通告要持续跟；成熟库有海量用户和 fuzzing
- **但**：做代理要**流式转发**（不整体解析 body），所以仍需具备"只在字节流里找头边界、body 原样转发"的能力——这正是手写一遍的意义：知道边界在哪，才能在需要时绕过库

### 8. 什么时候该自己写、什么时候该用库？

- 判据：**这件事是"产品的差异化价值"还是"通用基础设施"**
- 通用基础设施（HTTP 解析、TLS、JSON）→ 用库，自己写只是重造别人测过的轮子
- 差异化部分（怎么切分 AI 流量、怎么还原调用链、怎么统计 usage）→ 必须自己写，而且要写到能控制每一层
- 手写一遍的价值不在"以后自己写"，在"知道库替你做了什么、边界在哪、什么时候必须绕过它"
