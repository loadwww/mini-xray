# M6 · 图与报告

### 1. 为什么输出 Mermaid 而不是生成 PNG？

- Mermaid 源码是**纯文本**：可 diff、可 grep、可进 git、可被 CI 断言结构，PNG 是二进制黑盒
- 文本可由渲染器（GitHub / mermaid.live / 前端 mermaid.js）按需出图，同一种数据能换主题和布局，不用在 C++ 里排版
- 生成 PNG 要把字体、DPI、布局算法拖进依赖链；纯字符串函数零依赖、跨平台字节一致
- 判据：**产物需要被机器比较或人类二次编辑时，优先文本格式**；只有最终展示样式固定且不可变时才考虑位图

### 2. 原子写为什么必须 rename？直接覆盖有什么风险？

- `ofstream(path, trunc)` 一打开就把旧文件清空；写到一半崩溃/断电，读者看到的是**半截 JSON**且旧版本已丢失
- 正确顺序：同目录写 `.tmp` → flush + close（确认无错）→ remove 旧目标 → rename 覆盖
- 同目录是关键：跨文件系统的 rename 不保证原子，还可能落到不同磁盘
- `meta.json` 最后写，把它当**完成标记**：读者看到它存在就认为同批产物齐全，避免逐文件探测
- 幂等来自"每次全量重写 + 相同输入相同输出"，不是"追加写"；重复执行不应产生重复文件

### 3. meta.json 为什么要存降级计数？这些数字对用户意味着什么？

- `parse_failed` / `dropped_events` 是**数据完整性的度量**：图好看不代表证据全，缺事件意味着结论可能偏
- 把降级显式写进产物，是"诚实性"要求：用户能判断这份报告能信几分，而不是被静默丢弃骗过
- 判据：任何"尽力而为"的环节（队列丢弃、解析失败、推断值）都要留痕，让下游能区别"真的没有"与"没看到"

### 4. 报告和 Web UI 的数据来源应该是同一个吗？为什么？

- 应该是**同一个数据模型**（M5 的 `Run`），而不是同一份渲染代码：两者回答的问题不同（离线可读摘要 vs 在线交互浏览）
- 数据同源保证数字一致；展示分层保证各自能用最合适的媒介（Markdown 字符串 vs JSON API + HTML）
- `emitReport(Run)` 做成纯函数（不碰文件、不碰 HTTP）才能被验证台直接断言，也是"渲染层与 I/O 层分离"的通用判据

### 5. 节点 id 与显示标签分离，解决了什么问题？

- 标签（模型名、工具名）会重复、含空格和特殊字符，直接拿来当 id 会冲突或让 Mermaid 语法失效
- 用 `s0` / `t1` 这种**稳定且唯一**的 id 做引用边，标签只负责人类可读，并对 `"`、`|`、换行做转义
- 通用模式：内部标识用不可变短串，展示文本单独字段；改文案不应影响边的连接关系

### 6. HTML 实体转义为什么必须在生成时做，而不是交给渲染器？

- 生成的是图描述语言，不是 HTML；`&`、`<`、`>` 在 Mermaid 标签里有语法含义，留给渲染器只会得到解析错误或注入
- 转义要在**数据进入模板的边界**做一次，而不是在每个消费者的末尾补;否则两个消费者会一个转义、一个漏掉
- 验证方式不是"看着对"，而是造一个含 `|`、反引号、换行的输入，确认输出仍能被解析器接受
