# M4 · SSE 流式

### 1. chunked 和 SSE 是两层分帧，别混成一个东西

- **chunked** 是 HTTP 传输层编码：`长度前缀 + 数据块`，`0` 后跟空行表示 body 结束。它只管"这一段字节到哪为止"
- **SSE** 是应用层文本协议：`data:` 行、空行分隔事件。它骑在 body 里面，管"一个事件到哪为止"
- 判据：**解码顺序固定是从下往上**——先按 chunked 还原字节流，再按 SSE 切行和分组。反过来永远得不到完整事件
- 一个 chunk 可能含多个事件，也可能把一个事件切成两半；一层解决不了另一层的边界问题
- 现成的 HTTP 客户端库通常已在内部解掉 chunked，再回调给业务层；手写解码器的价值在于离线解析抓包文件

### 2. 流式转发为什么必须拆成两个线程？

- 客户端侧 `send()` 是**同步**的：阻塞到整个 body 收完才返回；服务端侧 handler 是**回填**的：必须先返回、库才开始往客户端写
- 一个"必须阻塞到收完"，一个"必须立刻返回"，同一线程里不可能同时满足
- 解法：把 `send()` 挪到独立线程，中间放一个**线程安全的有界字节队列**，下游用 provider 反复来取
- 判据：**谁阻塞谁、谁先返回**要能画成时序图；画不出来说明职责还没拆干净

### 3. 队列满了：丢还是等？

- **受控降级（丢 + 计数）**适用于"少一条不影响结论"的数据，比如审计事件：链路图缺一条边仍可读
- **背压（生产者阻塞）**适用于"少一字节结论就错"的数据，比如字节流：丢一段 `data:` 会让 JSON 残缺，整段回答作废
- 阻塞带来的副作用正好是想要的：生产者停 → 不再读 socket → 上游 TCP 发送窗口填满 → 上游自己慢下来，整条链对齐到最慢一环
- 为什么必须有上界：客户端断网但 TCP 未超时的几十秒里，无限队列会把内存吃光
- 判据一句话：**丢得起就丢，丢不起就等，但永远要有上界**

### 4. 条件变量里 wait / notify 各归谁？

- `wait` 归**消费者**（等"有数据"或"该收工"），`notify` 归**生产者**（改了状态之后）
- 谓词必须是 callable，且要包含**终止条件**（如 `closed_`），否则关流时等待者醒不过来、join 永远等下去
- 一个条件对应一个 cv：多个等待条件共用一个 cv 会互相唤醒、空转一轮
- `notify` 放**锁外**：持锁 notify 合法但被唤醒者立刻又阻塞在锁上，白多一次上下文切换
- `pop()` 必须在解锁前完成；`join()` 必须在锁外调用（锁内 join 是经典死锁）
- **`wait(lk, pred)` 的 pred 不是 bool**——传 bool 是编译期错误，传"bool 的值"更是逻辑错误

### 5. 流式解析为什么需要两级缓冲？

- 第一级 **半行**：字节流可能把一行切成两半，没见到 `\n` 之前不能确定这是一整行
- 第二级 **半事件**：SSE 的事件边界是**空行**，不是换行；多行 `data:` 要拼成一个事件
- 关系：`字节 --(\n 切行)--> 行 --(空行分发)--> 事件`
- 每一级都"见到边界才交出去"，这是所有增量解析器的通用形态（HTTP 头、protobuf、日志行同理）
- `\r\n` 要在切行时剥掉行尾 `\r`；`p == 0`（空行）时注意 `size_t` 下溢：`p-1` 会变成极大值

### 6. SSE 行规则里最容易错的四条

- **边界是空行**，连续空行不应产生空事件
- `data:` 后的空格是惯例不是语法；只剥**一个**，data 内容本身允许以空格开头
- 多行 `data:` 按规范用 `\n` 拼接，剥空格要针对**每一行新追加的段**，不能看累积缓冲的首字符
- `:` 开头是注释（心跳），`[DONE]` 是应用层约定不是 SSE 规范；区分"传输层结束"和"语义层结束"

### 7. 解析坏数据为什么要"计数跳过"而不是让异常飞？

- 流式数据源不完全可信（ proxies、截断、上游 bug），一个坏块只是局部脏数据
- 异常逃出线程函数 = `std::terminate`，整条链路报废；计数跳过 = 损失可观测、可度量
- 前提：**计数器要暴露出来**，否则"静默跳过"等于把错误藏起来
- 提取字段前必须 `contains` + `is_xxx` 双判；JSON 里 `null` 不是字符串，`get<std::string>()` 会抛
- 非 const 的 `json::operator[]` 遇缺键会**插入 null**（不是抛异常）；链式下标在中间层缺失时才会炸

### 8. 事件 schema 怎么演进才不弄坏历史数据？

- 老事件类型的字段集合**一个都不能加**：老解析器按固定形状写，"字段存在"和"字段有值"从此分不清
- 新事件类型只**多**带键，按 `type` **条件输出**
- 流内序号和全局行号是两回事：全局 seq 由记录器在入队时分配（近似观测顺序、连续无空洞），流内 index 才是检查"chunk 顺序与到达顺序"的依据
- 判据：**加类型 / 加键 = 兼容；改老键含义或删键 = 破坏性**

### 9. 在线记录和离线重放，为什么必须记"原始字节"？

- 记解析后的结论，等于让重放抄自己的答案：解析器写错了两边一起错，对账全绿却什么都没验证
- 记原始字节，重放必须真的重新跑一遍同一个解析器，才能抓出"字节被改了 / 块丢了 / 顺序乱了"
- 两边必须共用**同一个**解析器实现，否则对账失效；要独立验证还需要按规范另写的 golden 样例
- "没有结束标记"本身是一条信息：进程被杀留下的半截流必须标成 incomplete，不能把半句话当完整回答
- 幂等收尾：正常结束和客户端断开都可能触发收尾，结束标记只能写一次

### 10. 两个钟各管什么？

| 钟 | 用途 | 判据 |
|---|---|---|
| `steady_clock` | 耗时、超时、背压等待 | 单调不回退；系统时间被 NTP 改了也不会出现负耗时 |
| `system_clock` | 事件时间戳 `ts_ms` | 要能和别的系统日志按"几点"对上 |

- HTTP 库的"读超时"是**两个字节之间最多等多久**，不是整条流的总时长；流式响应思考久了会被库自己掐断，报的还是 `Read`（看起来像上游挂了）

### 11. 跨线程对象的生命周期怎么保证不悬空？

- handler 返回后 provider 可能还在被库反复调用 → 捕获 handler 的局部引用/字符串必然悬垂
- 用 `shared_ptr` 共享状态：谁最后放手谁销毁；拷贝 `std::function` 时各持一份
- detach 的线程不能 join，但必须**自己有终止条件**（上游说完 / 出错 / 被 abort），否则进程退出时还在跑
- 客户端断开的判据通常是 `sink.is_writable()` 或 `write()` 返回 false；两条路径都要触发收尾，才不会留下"有头无尾"的记录

### 12. 自测：进程在第 10 个 chunk 时被杀，文件里有什么？能恢复吗？

- 有：前 9 条 chunk 事件、req 事件（可能还有更早的 resp）；**没有**结束标记
- 没有：最后一块、总结事件、累积文本——异步写线程队列里没写完的也会一起丢
- "能不能恢复"要分两层：**字节层面不能**（丢的就是丢了）；**语义层面可以明确标注不完整**，让重放报 incomplete 而不是伪造一条完整回答
- 这也是"受控降级"的代价：宁可少几条，也不能让代理因为记日志而 OOM 或阻塞转发
