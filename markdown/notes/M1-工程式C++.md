# M1 · 工程式 C++

### 1. RAII 靠什么语言机制保证析构一定执行？栈展开是什么？

- 编译器在每个**作用域退出点**自动插入析构调用，三条路径：①正常走到末尾 ②`return` 提前走 ③**异常抛出**
- 第三条就是**栈展开**：异常从抛出点往上找 `catch`，每穿过一层函数帧，就执行该帧局部对象的析构。需要编译器为每个函数生成"清理代码表"——MSVC 由 `/EHsc` 控制，没有它异常穿帧时不析构（`C4530` 就是这件事）
- 顺序：后构造的先析构（倒序）
- **不生效的场合**：`abort()` / `std::terminate`、`std::exit()`（只清 static，局部对象不析构）、进程被强杀。RAII 保证的是"正常退出路径"

### 2. 什么时候用 `unique_ptr`，什么时候用值语义？

- 判据：**所有权归谁需要在运行时决定，才用 `unique_ptr`**；其它一律值语义
- 三个真正需要 `unique_ptr` 的场景：运行时多态（基类指针持派生对象）、工厂函数（运行时决定造什么）、pimpl（头文件不暴露实现）
- 值语义的好处：零堆分配、对象连续、拷贝/移动语义自动生成、异常安全免费
- 可空性不需要 `unique_ptr`——`std::optional` 表达"可能没有"，语义更准确
- 对照：`shared_ptr` 只在**真的多方共享所有权**时用；用它是设计信号，不是默认选择

### 3. `std::string_view` 什么时候悬垂？

- 它只有**指针 + 长度，不拥有内存**，背后那块内存没了或搬了，它就悬垂
- 典型四个场景：
  1. 绑定临时对象：`std::string_view sv = std::string("abc");`（临时语句结束就死）
  2. 源 `std::string` 被改动导致重新分配（小字符串有 SSO，超过约 15 字符才搬 → 这类 bug 会"偶尔"出现）
  3. 函数返回指向局部变量的 view
  4. 指向 `vector`/`string` 的元素，之后容器扩容了
- 只在函数体内用完就丢是安全的；**存起来**（成员、返回、放进容器）就必须换成持有副本的 `std::string`
- 另一个坑：view **不保证 `'\0'` 结尾**，不能直接喂给要求 null-terminated 的 C API

### 4. 为什么线程安全的追加写入器只需锁住"整行写入"这一步？

- 判据：**锁要罩住"共享可变状态"被访问的每一处，多一分浪费并发，少一分不安全**
- 序列化只读本条记录、只写线程局部变量，不碰共享状态 → 锁外做
- 真正共享的是文件句柄和写偏移 → 只有写那一步需要互斥
- 前提必须成立：**整行（含换行）在锁外拼成一个字符串**，锁内只有一次 `write`；拆成"写内容 + 写换行"两次，就退化成可交错
- 纪律：`std::ofstream` 的 `<<` 不是原子操作；`nlohmann::json` 对象不是线程安全的

### 5. 配置错误时"报错退出"还是"用默认值"，判断依据是什么？

- 判据：**这个缺失/错误会不会让程序在不自知的情况下做错事**
- 可降级：文件不存在（用户没配，用默认值合理）、单条规则坏（跳过它比整份报废更可用）
- 必须致命：JSON 语法错、结构性字段缺失、类型错——因为"错的规则比缺的规则危险"，静默用一个半截配置比直接报错危险得多
- 实现上让"失败"无法被忽略：致命走 `std::optional`/异常，降级走默认值 + stderr 警告（warn 不进 stdout，别污染数据流）

### 6. 为什么 `main` 要薄？

- `main` 是 C++ 里**唯一不能被调用的函数**：标准禁止递归调用、取地址、声明为 `static`/`inline`/`constexpr`
- 逻辑写进 `main`，这段逻辑就再也无法被第二处代码复用，也无法被测试
- 拆出 `int run(int argc, char* argv[])` 后，测试可以直接调用并断言返回值，不用起子进程、不用抓 stdout 文本
- 顺带好处：`main.cpp` 依赖面最小（只 include 入口头），改业务代码不必重编它

### 7. 为什么 JSONL 比"一个大 JSON 数组"更适合边写边读？

- **追加安全**：数组必须以 `]` 收尾，再放元素要回头改文件末尾（改 `]` 为 `,新元素]`）；JSONL 每行独立，永远只是往后 append
- **流式可读**：读到 `\n` 就拿到一条能独立 `parse` 的记录，不用等整个文件；大文件不必整体进内存
- **局部损坏**：一行坏了只丢一行；JSON 数组少一个逗号 → 整个文件 `parse` 失败 → 全部数据报废
- 代价：不能一次性 `parse` 整个文件，得逐行读；文件里混进半行（进程被杀）时要能容忍

### 8. 测试通过能不能证明"不加锁也没事"？

- 不能。几十字节的 `write` 在多数环境下恰好缩成一次系统调用，不加锁也可能几百次全对
- 数据竞争是**未定义行为**：今天不炸、明天炸、换台机器炸，现象是没头没尾地少一行或半行
- 正确性来自"所有访问路径都拿同一把锁"这条**推理**，不是"测试跑通"这个**观察**
