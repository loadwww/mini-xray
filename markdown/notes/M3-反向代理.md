# M3 · 反向代理

### 1. 正向代理、反向代理、网关，三者的分界在哪？

- **正向代理**：代表**客户端**。客户端显式配置它（`http_proxy=...`），它知道"我要去外面"，并替客户端访问任意目标
- **反向代理**：代表**服务端**。它伪装成一台真实服务器（客户端以为它就是要找的那台），背后有一组上游，客户端不知道也不需要知道
- **网关**：反向代理的一种，但会**改写协议/语义**（HTTP → gRPC、REST → 内部 RPC），不只是转发字节
- 判据：**谁配置它、它替谁隐瞒**。客户端配置 = 正向；服务端部署、客户端无感 = 反向
- 抓 AI 流量必须用反向代理：agent 那边只能改 `BASE_URL` 指向一个 HTTP 地址，它不会读系统代理设置，也不可能去理解 CONNECT 隧道。**让它以为你就是 OpenAI**，是最省侵入的接入方式

### 2. 代理的上游匹配用"域名"还是"路径前缀"？

- **域名匹配**的前提是你真的是那台机器：客户端连 `api.openai.com:443`，DNS 解析到你的 IP。要这么做得改 hosts 或做 DNS 劫持 + TLS 证书，代价是"每个客户端都要动系统配置"和"必须持有可信证书"
- **路径前缀匹配**：客户端把 base URL 改成 `http://127.0.0.1:8080/v1`，请求行就是 `POST /v1/chat/completions`，`Host` 是 `127.0.0.1:8080`。代理只看 path 就能分派，零客户端侵入、不碰 TLS
- 代价：**路径的命名空间被代理借用了**。上游真实路径必须能从 `配置里的 base path + 剥完 match 的尾巴` 拼回来，所以 `match` 和 `url` 末尾那段必须配对写
- 端口也是判据：路径匹配几乎必然跑在明文 HTTP 上（本地回环），要做 HTTPS 就得自己管证书

### 3. "路径段前缀"和"字符串前缀"差在哪？

- 字符串前缀：`/v1` 是 `/v1beta/x` 的前缀 → 会把 Anthropic 的 `/v1beta` 请求错误地吸到 `/v1` 那条上游
- 路径段前缀：要求前缀之后**刚好是段边界**——`/`、`?`、或者**串已结束**
- 判据一句话：`/v1x`、`/v1beta` 不是 `/v1` 的子路径，`/v1/x`、`/v1?x=1`、`/v1` 才是
- 实现上不能靠 `starts_with` 糊过去；"串已结束"这一条最容易被漏——它让 `GET /v1`（不带斜杠）也能命中
- `'?'` 也要算边界：query 不属于路径，`/v1?x=1` 的路径部分是 `/v1`

### 4. 剥掉 match 之后，尾巴要怎么拼回去？

- 三件事必须都做：**空串补 `/`**、**首字符不是 `/` 就补 `/`**、**`url` 的 base 尾部斜杠去掉**
- 不做第一条：剥完是空串，拼出 `http://host/v1` + `""`，请求行变成没有路径的畸形请求
- 不做第二条：`/v1?x=1` 剥出 `?x=1`，直接拼成 `http://host/v1?x=1`——斜杠丢了，上游看到的路径是 `/v1`，query 却还在，语义漂移
- 不做第三条：`url: "http://host/v1/"` 拼出 `/v1//models`，多数上游会把双斜杠当不同路径直接 404
- 约定：**剥完的路径一定以 `/` 开头**。这是函数对调用方的承诺，不满足就是 bug，不该靠调用方兜

### 5. 转发时哪些 header 必须改、必须剥？

| 类别 | 例子 | 为什么 |
|---|---|---|
| 透传 | `Content-Type`、`Authorization`、`Accept` | 属于**端到端**语义：只有最终接收者才该读它，中间每一跳都不能动 |
| 重算 | `Content-Length`、`Host` | 长度必须匹配实际写出的 body；`Host` 要指向上游那台机器 |
| 剥掉 | `Connection`、`Transfer-Encoding`、`Keep-Alive`、`Proxy-Connection`、`TE`、`Upgrade` | **hop-by-hop**：只描述"这一跳"的连接行为，原样搬到下一跳就是错的 |

- hop-by-hop 的定义方式有两种：RFC 规定的固定名单，以及 `Connection: X, Y` 里**动态点名**的那些（被点名的也要剥）
- 不剥 `Connection: close` 的后果：上游据此关连接，但下游以为连接还能复用，下一跳就错位
- 不剥 `Transfer-Encoding` 的后果更隐蔽：库里已按 chunked 解完并重算了长度，再带这个头等于声明"我又编了一遍"

### 6. 为什么状态码和 Content-Type 必须原样搬？

- 代理"透明"的定义：**下游看到的一切都应该和直连上游等价**，除了明确的代理标记
- 改状态码的代价：上游 429（限流）被改成 200，SDK 的重试与退避全部失效，业务表现为"一直拿到空结果但不报错"
- 丢 Content-Type 的代价：JSON 与 SSE 都靠它区分，丢了之后客户端无法判断要不要按流处理
- 反过来说，代理**自己**产生错误（上游连不上、没有匹配）时，必须用自己的状态码（502/404）和自己的错误体，不能伪装成上游的响应
- 错误体形状应当贴近被代理的 API 的惯例（如 `{"error":{"message":...}}`），让下游 SDK 不必为"代理这一层"写额外分支

### 7. 为什么配置要在启动时校验，而不是"过滤掉坏的继续跑"？

- **读不懂** vs **互相打架**，两类问题处理方式相反：
  - 读不懂（缺字段、类型不对）→ 可以跳过 + 告警：可能是别人共享的配置、或新版本加的字段，丢掉这一条其余照常能用
  - 互相打架（两条 `match` 相同、`/v1` 与 `/v1/` 并存）→ 必须拒绝启动：**没有"正确的默认选择"**，选哪条都是在猜用户意图
- 过滤"无用的"上游是做不到的判据：运行时唯一能判的是"此刻有没有请求命中"，但"今天没流量"和"这条写错了"是两件事。按它过滤等于**替未来的请求决定它不需要哪个上游**
- 静态可查的（格式、冲突）在启动期查；运行时才知道的（主机活着吗、TLS 握得上吗）不属于配置错误，表现应该是 502 + 可读原因，而不是起不来
- fail-fast 的经济性：配置错误在启动那一秒暴露，成本是改一行重启；带病运行时暴露，成本是"流量错了三天才发现"

### 8. 代理的 handler 为什么不按 method 注册？

- 代理对 method 是**无感**的：GET 查模型、POST 发消息、DELETE 删资源，走的是同一段"解析→路由→转发→回填"逻辑
- 按 method 各注册一个，等于把 method 白名单写死在代理里。上游哪天支持 `PATCH`，你还得改代理代码——这是把**上游的能力边界**复制到了代理里，两份会漂移
- 做法：一个 catch-all 的 handler（路径用正则全匹配），内部只看 path/header/body
- 代价：404 之类的兜底要自己处理（没有匹配的路径不会落进任何 handler，除非你注册了全匹配）

### 9. "在路由之前拦截"这个钩子，什么时候会用错？

- 一类钩子的执行时机决定了它能看见什么。**pre-routing 阶段 body 还没读**——它适合只凭 method + path + header 就能下结论的场景：鉴权、限流、黑名单、重定向
- 代理必须**原封不动转发 body**，所以它必须排在"读完 body"之后。放在 pre-routing 里，拿到的是空 body
- 更隐蔽的后果：提前终止意味着 body 那几十个字节**留在 socket 里没人读**。在 keep-alive 连接上，下一个请求的解析会从残留的 body 字节开始，连接直接错乱——表现是"第一个请求正常、第二个莫名 400"
- 判据：**要读 body 的逻辑，一律放在 body 可用的阶段**。选钩子之前先问"它在我需要的数据准备好之后才跑吗"

### 10. 为什么"记录"必须异步，同步写盘会毁掉什么？

- 代理是流量**必经之路**：它慢 1ms，所有请求都慢 1ms。写盘是"不可预测的慢"——磁盘忙、杀毒扫描、网络盘掉线，一次 `write` 可能卡几百毫秒
- 同步写的后果不只是慢：延迟抖动会让上游的超时判断、SDK 的重试策略全部失真，而这些都是你要观察的对象。**观察行为改变了被观察对象**
- 异步的必要条件是:热路径只做内存操作（加锁、入队、唤醒），把 I/O 的不确定性甩给专职线程
- 同步写的另一个隐性成本：脱敏要跑正则，大 body 是毫秒级。这属于"落盘前"的工作，放进 handler 就是白送的延迟

### 11. 有界队列 + 丢弃计数，为什么比"无限队列"更对？

- 无限队列的结局是**内存被吃光**：上游持续来、磁盘持续慢，积压只会涨。进程被 OOM killer 杀掉时，你连"为什么死"都看不到
- 有界 + 满了丢弃 + 计数 = **受控降级**：宁可少记几条事件，也不能让代理因为"记日志"而死。丢了多少必须报出来，否则"丢"和"没发生"无法区分
- 丢新的还是丢旧的：队列是 FIFO，旧的马上就会被写出，丢新的代价是"最近一小段没记"——正好对应"磁盘跟不上的那一段"
- 计数器的意义：`written + dropped == 投入总数` 是一条可断言的不变式，测试里靠它证明"没有凭空消失"

### 12. 条件变量的 `wait` 和 `notify` 分别属于谁？

- **消费者 `wait`，生产者 `notify`**。反过来就是"敲门的人站在门口等自己开门"——生产者自己等 `!queue.empty()`，而此刻队列当然是空的，于是它睡下，没人能叫醒它
- `wait(lk, pred)` 的 `pred` 必须是 **callable**（lambda / 函数对象），不是那个表达式的**值**。传 bool 编译不过；写成裸 `wait(lk)` 则会被虚假唤醒坑死
- 谓词存在的唯一理由：**虚假唤醒**（spurious wakeup）。条件变量允许在没人 notify 的情况下自己醒，醒来必须重新检查条件
- `wait` 期间锁是**放开**的（这是它的核心能力，`lock_guard` 做不到，所以要用 `unique_lock`），醒来后重新抢回来
- `notify` 放在锁外：持锁 notify 会让被唤醒的线程立刻阻塞在抢锁上，白醒一次

### 13. 锁该罩多大范围？

- 原则：**锁只罩"共享状态的那一次读写"，不罩 I/O、不罩计算**
- 反例：写盘在锁内 → 一次磁盘卡 500ms，期间所有 `push` 被挡住，异步就白做了，等于把磁盘的慢传染回转发线程
- 反例：`join` 在锁内 → 被 join 的线程循环第一步就要抢同一把锁，**死锁**。凡是"等另一个线程"的操作，几乎都不该持锁
- 正例：取元素 + 弹元素是一个原子动作，**必须同在一个锁内**。把 `front()` 放锁内、`pop()` 放锁外，等于在无锁状态下改容器结构
- 判断方法：问"这一段持锁期间，别人能不能进"。如果答案是"别人必须等"，那就问"它等得合理吗"

### 14. 日志行是怎么被并发写坏的？

- `std::cout` 的每次 `<<` 各自加锁，但**整行不是原子的**。十几个 `<<` 连着打，两个线程就能交错成半行 + 半行
- 解法：先在内存里拼成完整一行（`ostringstream`），最后只做**一次** `<<`。这也是所有结构化日志库的通用做法
- 这层锁只能保证"行完整"，**不保证顺序**：两个线程谁先谁后由调度决定，需要严格顺序就得额外排序（用序号）
- 另一个容易忽略的：`std::cout` 连终端时是行缓冲（每遇 `\n` 刷），连管道/文件时是**全缓冲**（攒满约 4KB 才刷）。日志重定向到文件后不 flush，就会出现"早就处理完了、日志过几十条才冒出来"——排查现场时最需要的就是这一刻

### 15. 事件 schema 里哪些设计是为"后续消费"服务的？

- **配对**：一次交互拆成 `req` / `resp` 两条，靠稳定的 id 串起来。不合并成一条的理由是"它们发生在不同时刻"，合并要等到结束才能写，等于放弃实时性
- **序号**：在**入队时**分配而不是写盘时分配。写盘时分配等于行号，没有信息量；入队时分配表示"被观测到的先后"，而且是**连续无空洞**的——消费端靠它检测"有没有丢事件"
- **哨兵值**：`status: 0` / `latency: -1` 表示"还没有值"。用 0/-1 而不用 `null`，是为了让字段类型稳定（永远是数字），消费端不用到处判空
- **对外格式一次定死**：schema 是"给别人看的稳定接口"，改了等于让所有历史数据的解析器失效。所以要么版本化，要么一开始就想清楚
- 内容取舍：只记"实际转发出去的东西"（而不是客户端发来的全部），少而明确胜过多而含糊

### 16. 脱敏应该做在哪一层，为什么？

- 做的位置有两个候选：**入口**（收到就脱）和**出口**（写盘前脱）
- 选出口的理由：热路径上不做任何可避免的工作。正则替换是毫秒级开销，而它只服务于"落盘"这一个目的
- 必须脱的两类：**头里的凭据**（`Authorization`、`x-api-key` 一类的白名单）和 **body 里的 key**（`sk-` 前缀、`Bearer` token）
- 保留前缀（`sk-***`、`Bearer ***`）而不是整段抹掉：看日志时还能分辨"这是哪家的 key"，且不会破坏 JSON 结构
- 长度阈值的作用：`sk-` 后面少于 10 个字符的不动，否则普通文本里的片段会被误伤，日志反而失去可读性
- 铁律：**凭据永远不该以原文落盘**。日志文件会被复制、会被分享、会被放进工单
