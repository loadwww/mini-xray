# M8 · 工程化

### 1. 单元测试、selftest、e2e 各覆盖什么？为什么三层都要？

- **单元测试**：纯函数、无外部依赖，定位到"哪个函数算错了"，最快最便宜
- **selftest**：把各关验证台串成一个可执行入口，覆盖模块间协作（落盘 → 重放 → 还原），CI 一命令判定
- **e2e**：真起进程、真发 HTTP、真写文件，覆盖"接线"层——只有它知道端口没起、配置路径错、Ctrl+C 没 flush
- 三层不是重复：越往上越贵、越慢、越难定位，但越能发现"每个模块都对、拼起来不对"的 bug

### 2. 为什么 CI 必须靠退出码判断成败？

- 日志里的 "PASS" 是给人看的文本，可能被缓冲、被截断、被别的步骤打印出来；退出码是进程契约，稳定且唯一
- CI 的每一步本质是"跑一个进程，看它的返回值"；断言宏再漂亮，若进程返回 0，流水线就认为成功
- 配套约定：0 = 成功，1 = 运行失败，2 = 用法错误；脚本任何失败路径都必须**显式非零退出**
- 验证退出码真的接通：故意让一个断言失败，CI 必须变红——否则可能只是"打印了 FAIL 却返回 0"的假绿

### 3. fixture 回归相比手写断言，优势在哪？

- 手写断言表达"我认为这个函数该返回什么"；fixture 表达"这份真实输入就该得到这份输出"——后者能钉住**没想到的边界**
- 输入数据在文件里，可以随真实抓包增长，测试代码不变；新增场景 = 新增目录，不用改断言逻辑
- 输出比对结构化字段并逐元素定位，失败时能说"第几个 run 的第几步的第几个工具错了"，而不是一大坨 diff
- 判据：fixture 要**一个目录只钉一个边界**（最短路径、前缀链、system-only 排除、id 配对），混在一起就无法定位

### 4. README 里"诚实的 Limitations"是加分还是减分？

- 加分：它把"能做什么"的边界说清楚，避免用户带着错误预期来踩坑；这是可信度的来源
- 写法的判据是**具体而非营销**："并行工具耗时是推断值，标注 durationInferred"比"部分功能待完善"有用得多
-  limitation 应该来自真实代码路径（未实现命令、平台限制、队列丢弃、未挂接的 UI），不是自我贬低也不是TODO列表
- 对维护者自身也有价值：它是一张"如果有人来提 issue，先检查这些"的清单

### 5. 你的测试在什么情况下会"假绿"？

- 断言被注释掉、条件写反、失败计数没加到退出码上——测试跑了但没判定
- 测试依赖顺序或共享全局状态，单独跑通过、换个顺序就失效；用临时文件名撞车也会随机假绿
- 只断言"文件存在"不断言内容；产物写错目录、写空文件都能通过
- 验证台自身有 bug（比如 lambda 捕获临时对象导致 body 为空），断言两边都读到空值反而相等
- 防御手段：**改坏验证**——故意注入一个只影响部分 fixture 的 bug，确认红的集合恰好是预期的那些，再恢复

### 6. CI 双平台的价值在哪？为什么不能只跑开发机？

- 开发机是"已经配好的环境"，CI 是"从零 clone 的干净环境"——只有后者能验证 README 的 3 条命令真的够用
- 平台差异（路径分隔符、换行符、编码、信号、进程 API、编译器标准库实现）在开发机上永远测不到
- `windows-latest` + `ubuntu-latest` 的矩阵把"代码可移植"从口头承诺变成每次 push 的机械检查
- 代价是要维护平台分支；判据是**分支只出现在真正的系统差异处**（CMake 源列表、e2e 脚本、进程编排），业务逻辑必须平台无关
