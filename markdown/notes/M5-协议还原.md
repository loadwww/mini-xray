# M5 · 协议还原

### 1. 为什么要分三层数据模型（Run / Step / ToolExec）？

- **Run** = 一次用户任务（一串递增的 messages 前缀）；**Step** = 一轮模型调用；**ToolExec** = 一次工具执行
- 判据：**并行工具属于同一轮**——按 Step 能取"并行区间最大值"，摊平成 Run 下的平铺列表就丢了这个归属
- 模型层必须是纯数据 + 序列化：不依赖 HTTP 库、不碰文件 I/O，否则离线 replay 要把整个采集栈拖进来，单元测试也得造假 Request
- ADL 序列化（`to_json`/`from_json` 与类型同 namespace）让 `json j = run` 和 `j.get<Run>()` 自动找到正确函数；缺键/类型不符要安全回落默认值，不能让一条坏历史数据炸掉整次还原

### 2. 为什么"messages 前缀递增"能代表 agent 的一步？什么时候失效？

- agent 循环形态固定：模型输出 → 客户端执行工具 → 把结果追加进 messages 再发一次。每次请求的历史是上次请求历史的**严格超集**，所以前缀链 = 任务链
- 两个独立任务共享 system prompt 时前缀只有 system 相同——必须排除，否则串成一条链。判据：**共同前缀里必须有至少一条非 system 消息**才算父子
- 失效场景：agent **改写**历史（删消息、改内容、重排）而非纯追加；多轮对话里的显式重置；不同任务恰好发出相同的前缀文本（哈希命中但有歧义）
- 认知价值：这是"基于观测推断意图"的通用难题——证据不充分时宁可分错，也不要把无关事件串成因果链

### 3. 滚动前缀哈希省了什么？代价是什么？

- 朴素全量比较是 O(n²) 文本扫描（每对请求比一遍完整历史，含 system 和长工具结果）；前缀哈希把"前 k 条消息"压成短串，判前缀退化成**一次字符串比较**
- 关键在**链式**：`h[k] = H(h[k-1] + msg[k])`，只把单条消息哈希拼起来会丢失顺序信息，`[A,B,C]` 和 `[C,B,A]` 会撞
- 代价是**碰撞**：不同序列可能同哈希。本关保留全量版 `isStrictPrefix` 作对照，验证台断言两者一致——这是"快版本 + 慢版本对账"的通用工程手法
- 为什么不用 `std::hash`：标准允许它随实现/进程变化，稳定 id 要求"重放同一文件结果不变"，所以用 FNV-1a 固定算法 + 固定种子
- 稳定 id 三要素：根事件时间 + 根指纹 + 序号。绝不用 `nowMs()`——当前时间不是数据的函数

### 4. 流式与非流式为什么必须产出同一个提取结果？

- 三种输入形状（req body / 非流式 resp / sse_end 事件）字段位置不同，但结论类型相同——**差异被挡在提取层**，下游建链不写两遍判断
- OpenAI 字段位置易错点：`content`/`tool_calls` 在 `choices[0].message` 里，`finish_reason` 在 message **外**，`usage` 顶层与 choices 平级，`tool_call_id` 是 snake_case
- `usage.observed` 区分"没看到 usage"与"usage 真的是 0"——都存 0 会让统计把"未观测"算成"零消耗"
- 解析坏数据一律默认 + 计数，不抛异常：`value<T>(key, 默认)` 的 T 由默认值推导，`getObj` 返回 json 不能赋给 string

### 5. tool_call_id 是协议强制的吗？关联键的本质是什么？

- Chat Completions：模型响应 `tool_calls[].id`，客户端回填 `role:"tool"` 消息必须带 `tool_call_id`——缺了请求会被拒，这是 API 契约
- 新 API 改名不换思想：Responses API 用 `function_call.call_id` + `type:"function_call_output"` + `call_id`；Realtime API 也用 `call_id`
- 为什么不用 `name` 配对：并行调用两个同名工具（如搜两次）无法区分；不用顺序：并行执行结果乱序返回，且累积 messages 里有历史轮次的 tool 消息
- 老版 `function_call`（单数，无 id）靠顺序对应，已废弃——正因为容易错配
- 判据：**关联键由协议指定，解析器不能自己发明**；换协议时配对算法不变，只有提取层的字段名变

### 6. 并行工具耗时为什么只能推断？为什么要标注出来？

- 代理只能观察到一个区间：上一响应结束 → 下一请求开始。N 个并行工具共享它，拆不出单个工具的精确耗时
- 每个工具都记整个区间（120ms 区间 + 3 并行工具 = 各记 120，**不是**相加 360），且 `durationInferred=true`
- 标注是**诚实性要求**：UI 要打 `~`，让用户知道这是推断值不是测量值；真正的精确耗时需要工具执行端上报 start/end 时间戳
- 乱序流量里区间可能为负（下一请求时间戳早于上一响应），必须 `max(0, ...)` 钳制

### 7. "依据来源分级"（confirmed / inferred）的设计价值

- **confirmed**：协议明说（结果 JSON 带 `error` 键 / `is_error:true`），可信；**inferred**：只是文本里像失败（error/failed/exception/not found 词表），可能误报
- 判定顺序：**先高级后低级，先到先得**——可信证据优先，启发式放最后
- 词表扫整段文本（含 JSON 键名）：`"is_error":false` 也会因键名撞 "error" 子串被误报为 inferred。这是**接受的误报**，低置信级就是为此存在——验证台专门钉住这个行为
- 通用判据：当证据强度不同时，不要压扁成一个 bool，分级让下游（UI 颜色、报告排序）能区别对待

### 8. 缺结果为什么要产出空壳记录，而不是跳过？

- 缺结果（工具意图存在但 messages 里没有对应 id 的 tool 消息）本身是一条有效结论：可能是 agent 改写了历史、结果被丢、或工具超时
- 跳过会让"发起过但没结果"这件事从图上消失，报告失真；产出 `resultJson` 为空的记录则保留了证据缺口
- **错配比缺结果糟糕得多**：把 A 的结果填给 B，报告会给出错误结论且无法察觉；空结果至少让人看到"这里缺东西"

### 9. 小规模数据要不要上哈希表优化？

- 双层循环是 O(N×M)，但 N（单轮工具数）是常数级 1~8，M（消息数）几十到几百。最坏 8×200=1600 次短字符串比较，微秒级
- 哈希表要建 M 次插入（含字符串哈希），N 小时建表成本**高于**省下的查找成本；且引入"重复 id 谁胜出"的语义问题，与"第一条匹配"的既定行为冲突
- 大 O 描述增长趋势，不是绝对耗时。**先测量再优化**——这是算法题思维与工程思维的分水岭
- 什么时候才值得：N 也很大（单轮几百工具）且函数被高频调用（批量离线分析）

### 10. 就地修改容器元素时最常见的坑

- `Step s = run.steps[i];` 是**拷贝**，对 s 的赋值落不到原 vector；必须 `Step &s = run.steps[i]`
- 同类坑贯穿多个关卡：`auto &R = runs[...]`、条件变量里的引用捕获、provider 里捕获 handler 局部变量
- 判据：**凡是要改容器里的东西，先确认拿到的是引用还是副本**——尤其当函数签名是 `vector<T>& runs` 时，内部循环极易写掉引用
